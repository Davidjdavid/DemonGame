# DemonGame — working rules

**Start of every session: read DESIGN.md and PROGRESS.md first** (DESIGN's Amendments section overrides its
original text). Then read only the folder README / PROGRESS section for the system you're working on.
Sessions run out of context, so these files are the memory, not the chat.

## What this is
A plotless gameplay prototype of an SMT-style RPG for David: free-form demon negotiation (live Claude via the
artifact `sample` capability), press-turn combat, fusion, a small dungeon. Story comes later — no plot, lore,
setting or cutscenes. Placeholder dungeon theme only.

## How to work
- Stages (see PROGRESS.md for the current one). David said: keep working through stages without waiting for his
  input; at each stage end publish the artifact, write the checkpoint report into PROGRESS.md, push, continue.
  Stop and ask only if blocked.
- Build the smallest version that proves each stage. No extra features, no polish before Stage 5.
- Make reasonable calls yourself and log them in PROGRESS.md ("Decisions").
- Update PROGRESS.md at the end of every work block.
- Commit after each working step; push to `main` (David approved working directly on main).
- Test before every checkpoint: `npm test` (node:test unit tests) plus `npm run e2e` (Playwright headless
  playthrough of the stage using the scripted mock brain).

## Code rules
- Plain JavaScript ES modules, no framework, no build step. The page is `index.html` + `src/**`.
- Game rules live in pure modules (no DOM) with Node tests in `tests/`. UI code lives in `src/ui/`.
- Assets are separate files (never inline base64). Images ≤ ~512px tall, WebP or PNG, credited in
  `assets/credits.json`.
- Make targeted edits; don't rewrite big files. Script bulk work (images, demon data) in `scripts/`; don't paste
  large data into chat.
- One folder per system; systems talk through small documented data formats so a session only needs the format,
  not another system's internals.

## Layout
- `src/talk/` negotiation rules, prompt building, brains (live `sample` + scripted mock)
- `src/combat/` press turns, damage, skills, AI (Stage 2)
- `src/growth/` leveling, fusion, compendium (Stage 3)
- `src/dungeon/` generator + map data (Stage 4a)
- `src/data/` demon cards, skills, items (JSON as JS modules or .json)
- `src/ui/` DOM screens
- `src/platform/` artifact capability wrappers (`sample`, `db`) with fallbacks
- `scripts/` publish bundling, image pipeline, sims
- `tests/` node:test unit tests; `e2e/` Playwright runs

## Live Claude (`sample`)
- Only works in the published claude.ai artifact that declares `capabilities: {sample: {}, db: {}, user: {}}`.
  Load the `artifact-capabilities` skill before touching capability code; its `.d.ts` files are authoritative.
- `sample` is memoryless: every call sends the card, the history, mood/state and the output format; use
  `sample.json`. First call needs a user click (consent). Handle `null`, `not_granted`, `rate_limited` without
  looping.
- The conversation "brain" is an interface with two implementations: live (sample) and scripted mock (tests).
  Headless tests can't call live Claude; David tests live.
- Game code decides outcomes; Claude proposes. Clamp moodDelta, drop unknown `matched` ids, validate inventory.

## Not now
No plot/story bible/lore/cutscenes. No more than ~30 demons. No voice. No character or demon art drawn or
generated by Claude or any AI — public domain / CC0 only. No real people. Nothing sexually explicit (flirting is
homoerotic vibe only; youths and childlike demons are always flirt n/a).
